> Conventional Commit in English. Artwork is one drawing per session (SPEC §16).
>
> **Task 1 is done.** The rest are open; work them in order.

---

## Context

Two things prompted this, and they turn out to be the same thing.

**The bug.** Keeping a look in the album keeps the backdrop with it. `scene` is a `Slot` inside
`Look.equipped` (`src/model/slots.ts`), so `SavedTray` — which stores whole `Look`s — cannot help
storing where she was standing. Pressing the star to remember an outfit also remembers the meadow,
and wearing that outfit again drags the meadow back with it.

**The feature.** The game grows a world. Three modes: an outer world showing a map; a location
picked off that map (a house, a building) holding several environments (living room, bedroom); and
the character editor that exists today. A doll can be put inside an environment of a location. The
reference is Avatar World — reference, not a model to copy (SPEC §3).

They are the same thing because the fix _is_ the feature: the backdrop stops being something the
doll wears and becomes **where she is**. Once `scene` leaves `Look`, the album stores only the doll,
with no album-specific code at all.

Half of the foundation is already built and wired to nothing. `src/model/stage.ts`,
`src/model/stageReducer.ts` and `loadStage`/`saveStage`/`openingStage` in `src/lib/storage.ts` are
complete and tested; `stage:current` is never written in production. That work is not thrown away —
it is what this plan grows into `World`.

**Intended outcome.** The child opens the app onto a map, taps a house, walks between its rooms,
drags a doll into one, taps the doll to dress her, and puts her back. The doll stays where she was
left. The album keeps outfits, not places.

## Decisions taken with the user

1. **Placements persist.** A rail of dolls stands beside the stage. Drag one onto the environment
   and she stays there — through leaving the room, closing the app, everything. Drag a placed doll
   off the stage and she goes back to the rail. An environment may hold both.
2. **Dressing pops her back to full size**, on the stage she is already on, with her environment as
   the backdrop. No camera module: the dress-up surface stays exactly the one that exists today, and
   the ~2009 tests that cover it stay valid. It is also what the reference does — a dedicated
   dress-up screen.
3. **An environment takes one colour from her _and_ has fixed colours of its own.** She paints the
   wall or the sky; the furniture and the ground are drawn. A room derived entirely from one colour
   reads as monochrome, which `PROGRESS.md` already recorded as the scene's one weakness.
4. **First release: the map, House (bedroom + living room) and Park (meadow).** Two new drawings —
   the map and the living room; the two existing scenes are re-homed as environments.

Decided here, not asked: **the roster stays at two dolls**, as `DEFAULT_STAGE` already fixed. It is
one constant.

One consequence to look at rather than assume, once task 5 lands: `DEFAULT_STAGE` gives the second
doll `PALETTES.skin[2]` (`src/model/stage.ts:39`), deliberately, so the pair read as two people. With
the map opening first, the child now meets both of them before she has dressed either — where today
she only ever sees one. Watch that on the iPad; it is a five-minute change either way.

## The one rule this breaks

SPEC §4 says **one level of navigation**: no modal, no back button. A world with a map, locations
and environments is hierarchical by definition, so the rule as written cannot survive. It is
replaced rather than dropped, and the replacement is what the tasks below must hold to:

> Every move is made by **tapping a picture of the destination** — a building on the map, a
> thumbnail of a room, the doll herself. There is no chrome control, nothing stacks over anything,
> and every place is reachable in one tap from wherever she is. There is still no "back".

Concretely: the map is always one tap away (head of the places rail); every room of the current
location is always one tap away (the rest of that rail); dressing is entered by tapping a doll and
left by tapping her again _or_ by the room thumbnail at the head of the tray rail. Dress mode gains
**no** extra column.

## Architecture

### Mode is derived, never stored

```ts
// src/model/world.ts
export const modeOf = (world: World): Mode =>
  world.here === null ? 'map' : world.dressing === null ? 'place' : 'dress';
```

Three fields already answer the question, so a fourth `mode` field could only ever disagree with
them.

### The state

`src/model/world.ts` and `src/model/worldReducer.ts` grow out of `stage.ts` / `stageReducer.ts`
(renamed and extended; the files are deleted in the same commit).

```ts
export type DollIndex = 0 | 1;
export type Place = { locationId: string; environmentId: string };
export type Placement = Place & { /** 0..1 across the canvas. */ x: number };

export type World = {
  schemaVersion: 3;
  dolls: readonly [Look, Look];
  /** Where she is looking. `null` is the map. */
  here: Place | null;
  /** Which doll her taps dress. `null` is nobody — she is playing, not dressing. */
  dressing: DollIndex | null;
  /** Where each doll was left. `null` is "on the shelf". */
  placements: readonly [Placement | null, Placement | null];
  /** The colour she painted each environment. */
  colors: Readonly<Record<EnvironmentId, string>>;
};
```

`EnvironmentId`, not `string`. `Z`, `PARTS_BY_SLOT`, `BY_ID` and `THUMB_FOCUS` are every one of them
`Record<FiniteUnion, X>` precisely so that adding a member is a compile error, and a loose key here
would be the one place in the model that does not hold to it. `isWorld` strips a colour key that no
longer names an environment on read — the same guard as task 1, second instance.

Every `| null` above stays `| null` rather than becoming optional. `exactOptionalPropertyTypes` is
on, and it is exactly why `Stage.scene?:` needed the awkward key-dropping rebuild at
`src/model/stage.ts:62`. Do not tidy them.

`worldReducer` keeps the shape `stageReducer` already proved: every existing `LookAction` arrives
wrapped and goes straight to `lookReducer` untouched.

```ts
export type WorldAction =
  | { type: 'dress'; action: LookAction } // unchanged from stageReducer
  | { type: 'dressDoll'; doll: DollIndex | null }
  | { type: 'goTo'; place: Place | null }
  | { type: 'place'; doll: DollIndex; at: number }
  | { type: 'takeAway'; doll: DollIndex }
  | { type: 'paint'; color: string };
```

`lookReducer` still never learns that there is a world above it, and neither does anything that
dispatches to it.

### The content layer — `src/world/`

Environments are **not** parts and do not enter `PARTS_BY_SLOT`. A part is worn on a doll; a place
is not. Keeping them out is what lets `Slot` shed `'scene'` entirely.

```
src/world/
  anchors.ts      # every map spot; every environment's floor line and doll scale
  colors.ts       # WORLD_COLORS — the fixed palette a place may paint with
  registry.ts     # LOCATIONS, the only import point for world art
  placement.ts    # pure: dollTransform(env, x), canvasX(clientX, rect)
  map.tsx         # the world map, with a building drawn at each location's spot
  locations/house/bedroom.tsx      # moved from src/parts/scene/bedroom.tsx
  locations/house/livingRoom.tsx   # new artwork
  locations/park/meadow.tsx        # moved from src/parts/scene/meadow.tsx
```

```ts
export type Environment = {
  id: string; // 'house.bedroom'
  /** Where her feet rest and how tall she stands here. */
  floor: { y: number; scale: number };
  defaultColor: string;
  render: (color: string) => ReactNode; // fills 0 0 680 540
};

export type Location = {
  id: string; // 'house'
  /** Where it sits on the map, and the disc a finger must hit. */
  spot: { x: number; y: number; r: number };
  environments: readonly Environment[];
};
```

`world/anchors.ts` holds **only the map spots**, and it holds them for the reason `anchors.ts`
exists: two files have to agree about them — the map artwork draws a building there and the tap
target sits on it, so a number chosen twice would drift. A `floor` line is the opposite case: only
its own environment ever reads it, so it is declared in that environment's file, and adding a place
stays one file plus one registry line.

`canvas` stays `0 0 680 540` for the map, for every environment and for the doll — one contract, and
`FILLS_CANVAS` in the contract suite already knows what to do with a backdrop.

The two re-homed scenes declare `floor: { y: 360, scale: 1 }` — their existing horizon, and the doll
exactly the size she is today, so nothing about them changes visually. New rooms drawn for a world
declare a smaller scale so two dolls fit.

### Rendering

`Doll.tsx` owns the outer `<svg>` today, which a scene holding two dolls cannot use. Extract the
layers:

```tsx
// src/render/DollLayers.tsx — the <g data-slot> list, no <svg>
// src/render/Doll.tsx      — unchanged public shape, now <svg>{<DollLayers/>}</svg>
// src/render/Scene.tsx     — <svg>{backdrop}{placed dolls in <g transform>}</svg>
```

`data-slot` must survive into `Scene`, because `App.slotAt` hit-tests it, and each placed doll needs
a `data-doll` beside it so a tap can tell which one. Zoom keeps rewriting the `viewBox` rather than
applying a CSS transform — that is what keeps the browser's hit test exact.

**Zoom is dress-only, and the SPEC amendment must say so.** `zoomedViewBox` crops around
`ANCHORS.dollBounds` (`src/lib/zoom.ts:20`), which means nothing in a room whose subject is the room
and where two dolls stand at different x. Keeping the slider inside the dress stage costs nothing;
making it work in place mode is the camera module decision 2 rules out.

`DraggableDoll` is **not** reusable in place mode, and saying "it reuses `useDrag`" is true of the
hook and false of the component: it hard-codes `useLook()`, `look.equipped[slot]`, `isPainted` and
`removeSlot` (`src/ui/DraggableDoll.tsx:47`). Place mode gets a sibling component. A `mode` prop
would take that file past both the complexity and the line cap.

### The shell

`App.tsx` is 88 lines against a 250-line ESLint cap, so the mode split moves out:

- `src/ui/MapView.tsx` — the map, plus a `TapTarget` per location's spot.
- `src/ui/PlaceView.tsx` — the environment, the dolls standing in it, the places rail, the dolls rail.
- `App.tsx` — picks the view from `modeOf(world)` and keeps the drop-zone/hit-test callbacks.

`src/state/WorldProvider.tsx` replaces `LookProvider`. **`useLook()` keeps its exact shape** — it
hands back the dressed doll and a dispatch that wraps every `LookAction` in `{ type: 'dress' }`. Its
seven consumers (`SlotBar`, `PartTray`, `ColorTray`, `ParamsPanel`, `SavedTray`, `RandomButton`,
`DraggableDoll`) all want exactly `{ look, dispatch }` over one doll, so **not one of them changes**.
A separate `useWorld()` exposes the world-level state to the three views.

There is no dressed doll in map or place mode, and `useLook()` must not invent one. It throws there,
the way it already throws outside a provider — all seven consumers mount only in dress mode, so the
throw is a guard against a wiring mistake rather than a case to handle.

Every new control is a thumbnail or a drawn shape, and every accessible name is a new key in
`src/i18n/locales/ptBR.ts` — `world.map`, `world.enter`, `world.room`, `world.doll`, `world.putHere`,
`world.takeAway`, `world.dress`, `world.leave`, `place.color`. `tests/integration/i18n.test.tsx:72`
pins key names to `/^[a-z][a-zA-Z.]*$/`: **no digits and no hyphens**, so an environment id used in a
key is `house.livingRoom`, never `house-1`. **Not one visible word is added**;
`dressUp.test.tsx` already asserts the whole rendered tree carries no text, and the new
`world.test.tsx` must make the same assertion for the map and place modes.

### Persistence

New key `world:current` at `schemaVersion: 3`. It skips 2 because `Stage` claimed 2 and never
shipped — the §14 amendment has to say so, or the gap reads as a lost migration. `stage:current` was
never written in production, so there is nothing to migrate from it.

**`look:current` _is_ migrated**, once, into `dolls[0]`. `PROGRESS.md` records a decision not to
migrate it, and the reason was sound then and is void now: it was that the backdrop left the look in
the same change, so a migration would have to guess which of two dolls a sky belonged to. Here the
sky belongs to neither — it belongs to the world — so the look becomes doll 0 and the scene is
simply dropped. The child keeps the outfit she is wearing.

**Deleting a slot does not repair on read. It throws.** This was checked in the source rather than
assumed, and it is the single most dangerous thing in the change:

- `findPart` is `INDEX[slot].get(partId)` (`src/parts/registry.ts:125`), and `INDEX` is built by
  walking `PARTS_BY_SLOT`. Drop `'scene'` from `Slot` and there is no `scene` key, so `INDEX['scene']`
  is `undefined` and `.get` raises a `TypeError`.
- `noUncheckedIndexedAccess` is on and does not help: it governs index signatures and arrays, not
  `Record<FiniteUnion, X>`, which TypeScript models as known properties. The compiler is certain
  `INDEX[slot]` is a `Map`.
- Two call sites feed it strings straight out of storage, both through the same unchecked cast
  `Object.entries(look.equipped) as [Slot, EquippedPart][]` — `sanitizeLook`
  (`src/model/sanitize.ts:42`) and `equippedLayers` (`src/render/resolve.ts:18`). `isLook`
  (`src/lib/storage.ts:26`) validates the _values_ of `equipped` and never its keys, so a stored
  `equipped.scene` sails through.
- `sanitizeLook` runs inside the `useReducer` lazy initialiser. **The failure is a white screen on
  the child's iPad, with her own stored look, and no test in this repository would see it** — jsdom
  suites start from empty storage.

So "repair on read is total" (SPEC §7a) holds for a part that leaves the registry and _not_ for a
slot that leaves the taxonomy. Closing that is task 1, before anything else moves: an `isSlot` guard
in `src/model/slots.ts` (a `Set(RENDER_ORDER)` membership test — `src/App.tsx:56` already validates a
DOM string exactly this way), applied in `sanitizeLook` and `equippedLayers` before the lookup.

Not `INDEX[slot]?.get(...)`: `strictTypeChecked` is on, `no-unnecessary-condition` would flag the
`?.` as redundant against the declared type, and silencing it would hide the type lie rather than
fix it. Not a stricter `isLook` either: `loadSavedLooks` _filters_ by it (`storage.ts:99`), so
rejecting an unknown key would delete the whole album entry instead of the dead slot. **Strip, do not
reject.**

The album needs the same treatment for a second reason. `loadSavedLooks` deliberately knows nothing
about the registry, so a kept look keeps its stale `equipped.scene`, and `replaceLook`
(`src/model/reducer.ts:73`) returns it verbatim — pushing the dead key straight back into live state
and into the next autosave. Worse, `signature()` and `withSavedLook` both dedupe on
`JSON.stringify`, so a kept look carrying a scene never matches the sanitized live one: it never
shows as worn, and pressing the star again adds a visually identical twin until the album fills with
duplicates. `SavedTray` therefore seeds through `sanitizeLook(kept, findPart)`, and the dedupe
signature becomes canonical (sorted keys) — `sanitizeLook` rebuilds `equipped` in iteration order
and `withFace` appends painted slots last, so two identical looks can stringify differently.

### 2 — `World` and `worldReducer` — **done**

Pure model, no UI. `src/model/stage.ts` and `stageReducer.ts` became `world.ts` and
`worldReducer.ts`; storage grew `loadWorld`/`saveWorld`/`openingWorld` and `CURRENT_WORLD_KEY` with
the one-time `look:current` migration; the `Stage` trio is gone.

Three refinements on what is written above, each of them settled in the doing:

- **`Place` is one name.** `here` is an `EnvironmentId` and the location is derived by `locationOf`,
  rather than `{ locationId, environmentId }` — two copies of one fact can disagree.
- **`dressing` and `placements` are independent.** A doll can be dressed before she is put anywhere.
  The one coupling is that `goTo` clears `dressing`.
- **`StoredWorld` is a type of its own.** `isWorld` checks a world is a world, `repairWorld` checks
  the rooms it names still exist. Keeping them separate is what stops `no-unnecessary-condition`
  from calling the second check redundant — which is precisely how the task 1 bug hid.

The taxonomy landed in a new `src/model/places.ts`, the counterpart of `slots.ts`: `LocationId`,
`EnvironmentId`, `isEnvironmentId`, `locationOf`, `environmentsOf`. Task 3's registry keys by it, and
`house.livingRoom` is deliberately **not** declared there yet — it arrives with its artwork in task 8,
so the taxonomy never names a room with nothing to draw.

One thing for task 4 to catch: `openingWorld` calls `withoutScene`, so `src/model/look.ts` now has a
caller outside the album. Both go at the same time.

## Where the gates will bite

- **`max-lines` 250.** `App.tsx` is the only file at real risk, which is why `MapView` and
  `PlaceView` are separate files from the start rather than extracted later. `SlotBar` (86) and
  `PartTray` (93) each gain one branch and stay well clear.
- **95% branches.** `World` introduces three nullable fields (`here`, `dressing`, and each
  placement), and every `null` is a branch. `modeOf` and `placement.ts` are pure and cheap to cover
  exhaustively; do that in tasks 2 and 6 rather than leaning on the integration tests to reach them.
- **`complexity` 10.** `stageReducer` sits at about 3 for three cases; six cases with any branching
  inside them lands at 8–9. It stays under only if **every case body is a named helper in
  `world.ts`** — which is exactly why `stageReducer.ts:30` is three one-line delegations to
  `withDressedDoll` / `nowDressing` / `withScene`. Copy that on purpose. The switch stays exhaustive
  with no `default`, so adding an action is a compile error until handled.
- **`src/ui/trays.tsx` at 259 raw lines** is the file closest to the cap already; it passes only on
  `skipBlankLines`/`skipComments`. Deleting the scene tray buys about 11 lines back. Do not add to it.
- **`src/world/registry.ts`** must be an index importing from `world/locations/**`, one line per
  place, mirroring `parts/registry.ts`. A flat object holding the art inline passes 250 at about four
  environments.
- **Unreferenced new files fail the gate immediately** — v8 reports every file under `src/`, tested
  or not. Nothing in `src/world/` may land in a commit that does not also test it.
